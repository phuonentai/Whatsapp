# Tasks: Equipo y permisos — rights management consolidado

Página consolidada `?view=access` con 3 tabs (Miembros / Matriz / Módulos), matriz read-only con metadata y preview de impacto; corrección de fuente de datos (wiring del servicio Stytch) y propagación de descripciones de rol. La política Stytch nunca se edita desde la UI.

## 1. Fundaciones [BE-INFRA] / [FE-NEXT]

> **Spike (1.1) — notas:**
> - **Modo de fallo de `GET /api/rbac/roles`**: `Handler.GetRoles` (auth/handler.go) SIEMPRE responde 200 con `RolesResponse`. Con el servicio Stytch cableado, un fallo de política (breaker abierto / API inalcanzable / caché vacía) hace que `StytchRBACService.GetAllRoles()` loguee y devuelva `nil` → respuesta `{roles: []}` (200 vacío). Nunca 500 hacia la UI. La matriz debe distinguir vacío = "política no disponible" con retry (nunca "sin permisos").
> - **Con servicio Stytch cableado devuelve**: roles de la política con ID normalizado (`stytch_` strip), `Name` display (roleName), `Description` de la política (task 1.3) y `permissions[]` con wildcards expandidos vía `expandWildcardActions` (recurso→acciones declaradas). Metadata del DTO genérica (display_name/description/category por recurso:acción).
> - **Audit log**: el ledger existente (`GET /api/crm/activities`, `ActivityTypeSistema` + `ActivityWithActor.realizada_por_nombre`) NO registra eventos de cambio de rol (la asignación va por la member API de Stytch, sin escritura al ledger). "Cambios recientes" usa el ledger existente (tipo `sistema`) + link al audit log; estado vacío cuando no hay eventos. Endpoints confirmados: `GET /api/rbac/roles`, `GET /api/auth/members`, `PUT /api/auth/members/{member_id}/role`, `POST /api/auth/members`, `DELETE /api/auth/members/{member_id}`, `GET /api/crm/activities`, `GET /api/modules` + `/api/modules/org`.
