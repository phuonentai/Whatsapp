STATUS: REJECTED

# Council Verdict: add-supplier-inquiry-agent

Reviewed `design.md`, `proposal.md`, and the delta specs (`supplier-inquiries`, `whatsapp-agent`). Premise claims were spot-checked against the living specs: rate limit (10 msgs/10s), `outside_24h_window` warning, outbox retry/backoff/dead-letter/`SKIP LOCKED`, consent state machine, PII masking decorator, composite tenant FKs, and escalation-always-allowed all match `whatsapp-outbound-send`, `durable-message-pipeline`, `whatsapp-compliance`, `crm-core-data`, and `agent-governance`.

The design is thorough on idempotency, tenant isolation, metering, and escalation. It is rejected because it contains one direct contradiction with a living spec, one undefined state transition that makes the run lifecycle non-terminating, and one unspecified side-effect atomicity boundary for order placement — each must be resolved in the design before implementation.

## Security Engineer findings

- **[HIGH] D3 contradicts `whatsapp-compliance` PII masking.** `whatsapp-compliance` requires the masking decorator to replace contact display names with `[NOMBRE]` in outbound prompts. D3 requires the drafting prompt to contain the supplier display name for the greeting. The design asserts "no contact PII beyond the supplier display name" but never reconciles this with the existing masking rule. Required change: decide explicitly whether the supplier display name is business identity (NIT persona jurídica, exempt from Ley 1581 personal-data masking) and how the masking decorator is configured/allowed to pass it through, or the greeting must use the masked placeholder. Without this, the implementation will either violate `whatsapp-compliance` or produce broken greetings.
- **[MEDIUM] Consent recorded `granted` at supplier creation jumps the compliance state machine.** `whatsapp-compliance` defines `none → requested → granted`. The DB CHECK (`valid_consent_status`) allows direct insertion at `granted`, but the design records `consent_grant` without stating the basis of the supplier's consent (org acts as controller; the platform is processor). Required change: state that the org certifies/evidences the supplier's consent (controller boundary) and that `consent_grant` is an org-declared grant, not a subject-initiated one — or require `requested → granted` via the existing path.
- **[MEDIUM] Cross-tenant guard for extraction/skip lookups relies on app-layer state.** The agent skip check and the procurement subscriber both resolve "sender → active run recipient" on every inbound `whatsapp.message.received`. The design does not state whether this lookup is tenant-scoped (organization_id from the event) and DB-isolated; a mis-scoped lookup would let one org's message suppress another org's recipient handling. Required change: specify the lookup as `(organization_id, contact_id)` scoped and transaction-isolated.
- **[LOW] No new secrets or credential paths** — verified clean; Stytch roles unchanged; override path audited with `member_id`; kill switch denies even with override (consistent with `agent-governance`). No action.

## DBA findings

- **[HIGH] `timed_out` has no driver — the run lifecycle cannot terminate.** `inquiry_responses`/recipients define `timed_out`, and `partially_answered`/`completed` depend on it, but no mechanism (timer, cron, or manual close) produces `timed_out` in this change; scheduling/follow-up is explicitly deferred. A run in `awaiting_responses` with an unresponsive supplier will never reach `completed`/`partially_answered`. Required change: define a terminating mechanism (e.g., an explicit manual close action or a max-age transition evaluated lazily on board read) or drop `timed_out`/`partially_answered` to a follow-up change.
- **[MEDIUM] Index set for the hot inbound path is not enumerated.** Every inbound WhatsApp message now triggers (a) the procurement subscriber's active-recipient resolution and (b) the agent subscriber's skip check. The design mentions "supporting indexes" without listing them; the lookup `inquiry_recipients(contact_id)` joined against active runs must be indexed to avoid a seq scan per message on a growing table. Required change: enumerate indexes (e.g., `inquiry_recipients(organization_id, contact_id)`, `inquiry_recipients(run_id)`, unique `(recipient_id, raw_message_id)`, `suppliers(organization_id)`, `products(organization_id, sku)`).
- **[MEDIUM] Run transition + outbox enqueue atomicity unspecified.** `draft → sending` and enqueueing one outbox event per recipient must be a single transaction (no send-without-enqueue or enqueue-without-transition); "all sends succeed → `awaiting_responses`" is a distributed condition evaluated by the dispatcher and must be guarded against concurrent kill-switch cancellation. Required change: specify the transaction boundaries and the conditional UPDATE for the aggregate transition.
- **[LOW] Duplicate NIT suppliers are unconstrained.** No uniqueness rule on `(organization_id, tipo_documento='NIT', numero_documento)`; duplicate suppliers would create duplicate contacts and split history. Recommend a partial unique index or explicit de-dup policy.
- **[LOW] Supplier-created contacts must set `source = 'manual'`** (CHECK: whatsapp/instagram/manual/import/api) and respect `consented_at` on `granted`; not specified.

## SRE findings

- **[HIGH] Order placement side effects have no atomicity or idempotency boundary.** The design lists send + negocio creation + actividad + `order_placed` audit without specifying ordering or failure semantics. If the confirmation is sent synchronously before the DB transaction commits, a failure leaves a sent confirmation with no deal (or a deal with no confirmation); if the endpoint is retried (double-click approve), duplicate sends and duplicate deals are possible. Required change: enqueue the confirmation send through the durable outbox inside the same transaction as the deal/actividad/audit, and guard duplicate placement (e.g., unique `(run_id, supplier_id)` order marker or an Idempotency-Key contract) so client retries are safe.
- **[MEDIUM] Kill-switch "pending sends not dispatched" must be enforced at dispatch time, not enqueue time.** Outbox events enqueued before the kill switch was enabled will be dispatched unless the handler re-validates run/recipient state (`cancelled`) transaction-isolated before sending. Required change: state that the send handler re-checks run status inside the claim transaction.
- **[MEDIUM] Rollback leaves in-flight outbox events.** Reverting the change strands queued `procurement.inquiry_send` events with no handler (dead-letter noise) and possibly unsent messages. Required change: note in the rollback plan that in-flight events are drained/cancelled or left to dead-letter with an operator action.
- **[LOW] Observability**: audits are specified but no metrics (LLM call counts, extraction failures, dead-lettered sends, run duration to completion). Recommend counters for procurement fan-out/extraction/order paths.
- **[LOW] Pacing mechanism unspecified across dispatcher workers.** "10 msgs/10s per organization" requires a token-bucket/gate keyed per org WhatsApp config shared by all workers, not per-worker counting. Recommend specifying the gate.

## Required design changes (numbered)

1. Resolve the D3 vs `whatsapp-compliance` contradiction: define whether the supplier display name passes the masking decorator (business identity, NIT persona jurídica) and how, or use the masked placeholder in greetings.
2. Define the basis of `consent = granted` at supplier creation (org-declared grant as controller vs. subject-initiated) and how `consent_grant` audit records that basis; confirm `consented_at` is set.
3. Define a terminating mechanism for unanswered recipients (e.g., explicit close action or lazy max-age transition) or defer `timed_out`/`partially_answered`; without it the lifecycle cannot reach `completed`.
4. Specify order-placement atomicity and idempotency: confirmation send via the durable outbox in the same transaction as negocio + actividad + audit, plus a duplicate-placement guard for retried POSTs.
5. Specify that outbox send handlers re-validate run/recipient state (`cancelled`/kill switch) transaction-isolated at dispatch time.
6. Enumerate the migration's indexes, including the tenant-scoped active-recipient lookup used by both the procurement subscriber and the agent skip check on every inbound message.
7. Add a rollback note for draining/cancelling in-flight `procurement.inquiry_send` outbox events.
8. Specify the per-org WhatsApp token-bucket pacing gate shared across dispatcher workers, and the LLM/outbound metric counters.
