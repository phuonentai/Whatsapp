# Stytch Enterprise Suite — Design

## Context

The product currently consumes a narrow slice of Stytch B2B: magic-link passwordless (custom email-first flow with membership pre-validation, `STYTCH_CONFIGURATION.md`), sessions (JWT + JWKS cache ≤300s, edge middleware `X-Forwarded-Auth`), policy-driven RBAC (`stytch-authorization`), org/member management, in-flight TOTP MFA (`mfa-totp-enrollment`, 14/15 tasks) and passkeys (`passkeys-sign-in`, 0/8). Stytch's free tier includes the full auth suite with no feature gating (SSO/SCIM 5 connections free, OAuth/OTP free, JIT/discovery free, Admin Portal free, 10K MAU, unlimited orgs; **paid**: Audit Logs $799/mo, bot detection/CAPTCHA/intelligent rate limiting add-ons, branding $99/mo, SMS per-message, $125/conn/mo beyond 5 — pricing figures per `## Assumptions`). Two living specs contradict each other: `crm-frontend` requires pre-built Stytch components + Admin Portal (`AdminPortalMemberManagement`, `AdminPortalSSO`); `stytch-nextjs-components` removed those mandates in favor of the custom form + custom member management. This change resolves the contradiction by adopting the Stytch surface for login, SSO, and SCIM while keeping the shipped custom member/role UI.

**Verified premises (codebase + SDK):**

- `POST /auth/signup` is PUBLIC and is the governed org-creation path: `BootstrapOrganizationWithOwner` → `Organizations.Create` + `Members.Create(SendInvite: true)` with slug-conflict retries, rollback, structured errors (`SLUG_CONFLICT`, `INVITE_FAILED`), and trial seeding (`trial_seeder.go`). Stytch discovery "Create Organizations" is DISABLED in the dashboard (`STYTCH_CONFIGURATION.md`).
- The custom login form lives at `app/auth/page.tsx`; `check-email` (`auth-email-check` spec, `GET /api/auth/check-email`) pre-validates membership locally; `sendMagicLink` (`lib/actions/auth/send-magic-link.ts`) only sends for existing members; `lib/auth/magic-link-limiter.ts` (in-process sliding window, per-email/per-IP, env-configurable) bounds sends today — but see D1: on the login path this limiter is retired with the custom form.
- `/authenticate` (`app/authenticate/page.tsx`) consumes magic-link tokens and continues MFA (TOTP) / passkey flows — unchanged by this change.
- Settings is a `?view=`-parameterized surface (`settings-content.tsx`, `settings-ui` + `admin-panel-navigation` specs): `?view=access` ("Equipo y permisos"), `?view=members`, `?view=subscription`, `?view=audit`; views are permission-gated via an allowlist (`org:manage` for access/members).
- The backend breaker pattern is `internal/platform/stytch` `Client.Run()` (threshold 5 / timeout 10s / half-open 2, `ErrCircuitOpen`); `MfaPolicyUpdater` (`organizations/domain/mfa_policy.go`) is the shipped template for a breaker-guarded org-settings mutation through `PUT /v1/b2b/organizations`, surfaced as `PUT /api/organizations/mfa-policy` gated `auth.RequirePermissionFunc("org", "manage")`, breaker-open → 503 structured error.
- `@stytch/nextjs/b2b` (installed 21.15.1) ships `StytchB2B` supporting `authFlowType: "Discovery"` with per-product config, plus `StytchB2BProvider`/`useStytchMember` (in use). **The Admin Portal exports (`AdminPortalSSOMountOptions`, `AdminPortalSCIMMountOptions`, `client.portal`) were NOT found in the installed `@stytch/vanilla-js@5.41.0` / `@stytch/core@2.64.0` type surface** (verified during council review; only the headless SSO/SCIM APIs — `sso.saml.createConnection`, `sso.oidc.createConnection`, `scim.createConnection` — and `render_b2b_admin_portal_*` telemetry events exist). See `## Assumptions` / D4 for the version-bump-or-fallback gate.
- Stytch B2B org-settings contract (`PUT /v1/b2b/organizations/{organization_id}`, verified against installed `stytch@12.43.0` `B2BOrganizationsUpdateRequest`): `email_jit_provisioning ∈ [RESTRICTED, NOT_ALLOWED]` (governs Email Magic Link **or** OAuth provisioning; no `ALLOWED` value exists), `email_allowed_domains`, `email_invites ∈ [ALL_ALLOWED, RESTRICTED, NOT_ALLOWED]`, `auth_methods ∈ [ALL_ALLOWED, RESTRICTED]` (default `ALL_ALLOWED`), `allowed_auth_methods` (enforced **only** when `auth_methods: RESTRICTED`; accepted values `sso`, `magic_link`, `email_otp`, `password`, `google_oauth`, `microsoft_oauth`, `slack_oauth`, `github_oauth`, `hubspot_oauth` — there is no `email_magic_link`, generic `oauth`, `passkeys`, or `m2m`), `sso_jit_provisioning ∈ [ALL_ALLOWED, RESTRICTED, NOT_ALLOWED]`, `sso_jit_provisioning_allowed_connections` (enforced when `sso_jit_provisioning: RESTRICTED`), `sso_default_connection_id`, plus the existing `mfa_policy`/`mfa_methods`/`allowed_mfa_methods`. **No org-level `sso_implicit_role_assignment` field exists** — SSO implicit roles are per-connection (`saml_connection_implicit_role_assignment` on update-saml-connection); JIT-provisioned members default to `stytch_member`. SSO connections: `POST /v1/b2b/sso/saml/create`, `POST /v1/b2b/sso/oidc/create`, `GET /v1/b2b/sso`, `DELETE /v1/b2b/sso/{connection_id}`.

## Goals / Non-Goals

**Goals:**

- Adopt the free Stytch B2B surface: pre-built login (discovery, OAuth, email OTP), per-org JIT domain join, SSO (SAML/OIDC) + SSO JIT, SCIM — with SSO/SCIM managed through the free Admin Portal (or the documented fallback, D4).
- One governed backend seam for org auth policy (`OrgAuthPolicyUpdater`) mirroring the shipped `MfaPolicyUpdater` pattern: breaker-guarded, `org:manage`, display-only mirror.
- Resolve the `crm-frontend` ⇄ `stytch-nextjs-components` spec contradiction in one coherent direction.
- Strict SSOT: no local credential/secret storage; auth-policy mirror never consulted for authorization (Stytch enforces at session mint / auth).

**Non-Goals:**

- Discovery/JIT org **creation** — platform `POST /auth/signup` remains the sole creation path.
- SMS OTP; paid add-ons (Audit Logs, bot detection, CAPTCHA, intelligent rate limiting, custom verdicts, branding).
- M2M tokens, impersonation, device fingerprinting, Stytch webhooks, event-log streaming (follow-up changes).
- `AdminPortalMemberManagement` / Admin-Portal roles editing — shipped `equipo-permisos` + in-flight `custom-roles-editor` remain.
- No DB migration; no new tables.

## Decisions

### D1 — Login surface: pre-built `<StytchB2B>` in Discovery mode, org creation hidden

`app/auth/page.tsx` renders the pre-built StytchB2B component (Discovery mode, `locale: "es"` + Spanish strings overrides — see D8) instead of the custom email form. The UI renders magic link, OAuth (Google/Microsoft, dashboard-configured), email OTP, and passkey methods per the project config; Discovery shows the member's orgs and any orgs they can JIT-join. Stytch's discovery org-creation toggle remains disabled, so the only way an unknown email reaches an org is via (a) an invite, or (b) a per-org JIT join the admin opted into.

- **Rationale (why X over Y):** the custom flow existed to prevent unknown-user emails and enumeration. With the pre-built UI, `magicLinks.email.discovery.send` accepts only an `email_address` and has no platform hook to block it — the platform's own `STYTCH_CONFIGURATION.md` documents that the Stytch UI "always sends emails." What the pre-built surface still guarantees is **org-existence concealment**: discovery authenticate lists organizations only for addresses that are members, invitees, or JIT-eligible (verified in the discovery contract), so orgs with JIT off and no membership are never revealed to unknown addresses. The send itself is NOT suppressible and the in-process `magic-link-limiter.ts` (per-IP/per-email sliding window) can no longer bound login-path sends because sends now happen client-side in the Stytch UI; Stytch's own per-email rate limit (~1 req/sec/email) is the sole send backstop. This is an accepted, documented posture change (`STYTCH_CONFIGURATION.md`, task 6.1). Alternatives rejected: keeping the custom form and bolting OAuth/OTP buttons onto it (re-implements what the free UI gives us; the old `crm-frontend` spec is right that pre-built wins); a headless custom UI (more code, same result).
- `lib/actions/auth/send-magic-link.ts` + the `/auth` `check-email` usage are retired unless other callers exist (verify in implementation; the `auth-email-check` endpoint may remain for tests/other callers — see verdict item 7 and the `auth-email-check` delta).
- Rate limiting: the login-path send bound moves to Stytch's per-email rate limit; `magic-link-limiter.ts` stays wired only on any remaining in-process send path (if one exists after the caller audit).

### D2 — JIT: per-org opt-in domain-restricted join; creation never

- **Join:** new org setting `email_jit_provisioning: RESTRICTED` + `email_allowed_domains`, exposed as an org-admin toggle ("Allow teammates with @<domain> to join automatically") in settings `?view=access`, default **off** (`NOT_ALLOWED`, unchanged for existing orgs). JIT-joined members get the default role (Stytch RBAC policy `stytch_member`); role escalation remains admin-managed. Opt-in JIT = opt-in discoverability: only opted-in orgs appear in Discovery for domain-matching emails. **OAuth-JIT implication (stated):** `email_jit_provisioning` governs provisioning via Email Magic Link **or** OAuth — enabling domain JIT also enables OAuth JIT for verified provider emails on the allowed domains; the UI copy and docs must state this.
- **Create:** never enabled (discovery org creation stays off; there is no org-creating `email_jit_provisioning: ALLOWED` value — the SDK exposes only `RESTRICTED`/`NOT_ALLOWED`) — preserves trial seeding, slug governance, and anti-squatting from `POST /auth/signup`.
- **SSO JIT:** enabled **per org by the org admin through the governed auth-policy surface** (the `?view=access` JIT card, extended with an SSO-JIT toggle shown when the org has ≥1 active SSO connection), NOT auto-flipped by the Admin Portal (the portal runs client-side and has no backend hook). Enabling writes `sso_jit_provisioning: RESTRICTED` scoped to `sso_jit_provisioning_allowed_connections: [<org's active connection ids>]` (least privilege — never `ALL_ALLOWED` org-wide) via `OrgAuthPolicyUpdater`; disabling writes `NOT_ALLOWED` and clears the list. JIT-provisioned SSO members receive Stytch's default `stytch_member` role (least privilege). Custom per-connection implicit roles are out of scope; if ever needed they are configured per connection via `saml_connection_implicit_role_assignment` on update-saml-connection (Stytch-side), not via the org policy.

### D3 — Backend: single `OrgAuthPolicyUpdater` seam

`organizations/domain` gains `OrgAuthPolicyUpdater` (typed enums mirroring `domain/mfa_policy.go`: `JitPolicy ∈ [DISABLED, DOMAIN_RESTRICTED]` mapping to Stytch `NOT_ALLOWED`/`RESTRICTED`, `SsoJitPolicy ∈ [DISABLED, CONNECTION_RESTRICTED]` mapping to `NOT_ALLOWED`/`RESTRICTED`, `AllowedAuthMethod ∈ [magic_link, email_otp, sso, google_oauth, microsoft_oauth]`, validation) implemented by the Stytch auth adapter via `PUT /v1/b2b/organizations/{organization_id}` behind the shared two-tier breaker. The write contract is the full org auth policy: `email_jit_provisioning`, `email_allowed_domains`, `auth_methods: RESTRICTED` (enforced-list mode — REQUIRED for `allowed_auth_methods` to take effect) + `allowed_auth_methods` (complete list, correct enum values), `sso_jit_provisioning`, `sso_jit_provisioning_allowed_connections`, `sso_default_connection_id`. Breaker-open/5xx → 503 structured error (`auth_policy_update_unavailable`), Stytch 4xx surfaces as a normal error. Exposed as `GET /api/organizations/auth-policy` (read mirror, display-only) + `PUT /api/organizations/auth-policy` (write), both gated `auth.RequirePermissionFunc("org", "manage")` — the exact `MfaPolicyUpdater` shape (`domain/mfa_policy.go`, `PUT /api/organizations/mfa-policy`). The **read path** maps breaker-open/unreachable Stytch to the same 503 structured-error family (`auth_policy_unavailable`) — mirroring the write path (verdict item 8).

- **First-write default preservation:** existing orgs keep `auth_methods: ALL_ALLOWED` until the first policy write (no surprise behavior change). On the first write, the updater reads the org's current effective method set (for `ALL_ALLOWED` orgs: the project-enabled methods relevant to the org — at minimum `magic_link`, plus `sso` when the org has active connections) and persists `RESTRICTED` + that preserved set + the requested additions. Unit-tested (task 2.2) and E2E-verified (task 7.3).
- **Rationale:** one governed seam for all org-auth-policy mutations instead of N ad-hoc routes; mirrors the shipped pattern so reviewers/tests get the same shape (success / Stytch 4xx / breaker-open→503 / validation).
- **Validation contract (`ValidateAuthPolicyUpdate`):** enum checks, non-empty domain allowlist when `DOMAIN_RESTRICTED`, at least one primary method, no duplicates, and `sso_default_connection_id` MUST reference an org-owned connection (verdict item 8; residual risk low — Stytch 4xx surfaces — but stated).
- **Authorization invariant:** the mirror is display-only; Stytch enforces auth methods + JIT at authentication time. No code path may gate on the mirrored values.

### D4 — SSO + SCIM: Admin Portal mounts (pending verification), fallback defined

Settings gains `?view=sso` and `?view=scim` rendering `AdminPortalSSOMountOptions` / `AdminPortalSCIMMountOptions` (from `@stytch/vanilla-js/b2b/adminPortal`), gated `org:manage` via the existing settings view-allowlist mechanism. The Admin Portal runs client-side with the member session: connection create/edit/delete, SCIM base URL + bearer token (shown once), group→role mapping — all managed in Stytch.

- **Availability gate (verdict item 5):** the Admin Portal exports were NOT found in the pinned `@stytch/vanilla-js@5.41.0` / `@stytch/nextjs@21.15.1` / `@stytch/core@2.64.0` type surface. Task 3.2 SHALL verify the exports against the installed version and record the outcome, then branch:
  - **Branch A (version bump):** if a reviewed `@stytch/vanilla-js` (and `@stytch/nextjs` if its b2b entry is needed) version ships the Admin Portal, bump the pins, review the new versions, update the "Dependencies: none new" claim in `proposal.md`/`Impact`, and proceed with the mounts.
  - **Branch B (fallback, if unavailable in any reviewed version):** Go-backed connection CRUD — SSO/SCIM adapters in `internal/platform/stytch` (`sso.saml.createConnection`, `sso.oidc.createConnection`, `sso.deleteConnection`, `GET /v1/b2b/sso`, `scim.createConnection`, `scim.deleteConnection`, `GET /v1/b2b/scim`) exposed as `GET/POST/DELETE /api/organizations/sso-connections` and `GET/POST/DELETE /api/organizations/scim-connections` gated `org:manage`, behind the shared breaker, with minimal custom admin forms in `?view=sso`/`?view=scim`. Secrets still never transit or persist on the platform (SCIM bearer token shown once per Stytch's API contract; never stored locally). If Branch B is chosen, the `crm-frontend`/`enterprise-sso`/`scim-provisioning` deltas are revised to match via the change workflow before FE tasks are sized.
  - Decision recorded in task 3.2 before FE implementation proceeds.
- **Rationale:** the Admin Portal is free, complete, and removes the SSO/SCIM UI build entirely. Rejected alternatives: custom SSO-config forms (build cost with zero marginal value; the old `crm-frontend` mandate pointed here too); Go-side connection CRUD as the primary path (unnecessary if the portal is available — no platform logic needs those calls; it is the documented fallback only).
- **Secrets:** SCIM bearer tokens and IdP client secrets/certs are never transmitted to or stored by our servers; they exist only in Stytch.

### D5 — Settings view routing + gating

`settings-content.tsx` registers `?view=sso` and `?view=scim` in the existing view allowlist with `org:manage`, linked from the settings overview, per the `settings-ui` view-command pattern. Non-`org:manage` users do not see the entries.

### D6 — Member management stays custom

`?view=members`/`?view=access` keep the shipped custom UI (`equipo-permisos`); `AdminPortalMemberManagement` is NOT adopted, and the `custom-roles-editor` change proceeds as designed. Only SSO and SCIM management move to the Admin Portal (or fallback, D4). The `crm-frontend` requirement is reconciled to say exactly this (resolving the contradiction with `stytch-nextjs-components`).

### D7 — OAuth + email OTP enablement

Dashboard-configured per project: Google + Microsoft OAuth providers; email OTP enabled as a primary method, exposed per org via the auth-policy surface. **Semantics (verdict item 3):** `allowed_auth_methods` is enforced ONLY when `auth_methods: RESTRICTED` — so any per-org method control writes `auth_methods: RESTRICTED` plus the complete `allowed_auth_methods` list; the current default (`ALL_ALLOWED`) is preserved for orgs that have never saved (D3 first-write rule). Enum values are the SDK's: `magic_link`, `email_otp`, `sso`, `google_oauth`, `microsoft_oauth` (no `email_magic_link`, no generic `oauth`, no `passkeys`/`m2m` — passkeys are rendered by the UI per project config, not per-org `allowed_auth_methods`). The pre-built UI renders the enabled methods. No custom OAuth callback code: the UI + `/authenticate` token consumption handle it.

### D8 — Spanish locale on the pre-built surfaces (verdict item 8)

The current custom flow renders Spanish copy (`lib/copy/ui`); `StytchB2B` and the Admin Portal default to English. The SDK supports `locale` (`en | es | pt-br | fr`) and strings overrides (verified in the SDK types): task 4.1 pins `locale: "es"` (plus any required strings overrides) on the `StytchB2B` config, and task 3.2 does the same for the Admin Portal mounts — so the auth and SSO/SCIM surfaces match the product's Colombian-Spanish mandate.

## Risks / Trade-offs

- **Unknown-email discovery sends return with the pre-built UI** (custom pre-validation gone): every submitted address triggers a discovery send; the in-process `magic-link-limiter.ts` can no longer bound login-path sends (client-side), and Stytch's per-email rate limit (~1 req/sec/email) is the sole backstop. Org-existence concealment is preserved (discovery lists orgs only for members/invitees/JIT-eligible addresses). This posture change is documented honestly in `STYTCH_CONFIGURATION.md` (task 6.1) — the earlier design text claiming the send vector is "bounded without custom code" is retracted (verdict item 4).
- **Org squatting / namespace exposure via JIT join** → domain-restricted (`RESTRICTED` + `email_allowed_domains`), default member role, orgs opt in knowingly; org *creation* via JIT/discovery stays off so tenant creation remains governed.
- **SSO connection budget (5 free)** → documented in config and `## Market & Unit Economics`; OAuth social is not connection-billed; the 6th SSO/SCIM org costs $125/conn/mo — pass-through to the Enterprise tier (commercial decision, not a code gate).
- **Billing verification prerequisite** — magic links to arbitrary customer emails require billing verification on the Stytch project → recorded as an OPS-GOV gate before E2E with real addresses.
- **Admin Portal availability/version risk (verdict item 5)** — the Admin Portal exports were NOT found in the pinned SDKs; the mount renders Stytch-hosted UI whose styling/behavior is Stytch-owned. Task 3.2 is the decision gate: version bump (reviewed pin) or the documented Go-backed fallback; E2E in the test project verifies the chosen surface before prod.
- **Spec-reconciliation fragility** — modifying two living specs risks drift if the delta headers don't match → full requirement blocks copied verbatim into deltas (per OpenSpec MODIFIED rules), validated by `openspec validate`.
- **Posture shift for enumeration** — discovery reveals org existence for opted-in orgs only; unknown-address sends are not suppressible (D1). Accepted as the pre-built-UI trade-off; spam/abuse posture documented and monitored (`## Market Risk`).

## Market & Unit Economics

Scope: this change is market-in-scope (pricing posture, signup funnel, SSO/SCIM connection budget, WhatsApp/Meta-adjacent auth surface for a Colombian B2B CRM). Figures are assumptions pending dated re-verification at task 6.3.

- **Free-tier MAU headroom vs. enterprise seats:** the free tier includes 10K MAU. SSO/SCIM/JIT-provisioned members count toward MAU only when they authenticate in a billing month. A Colombian enterprise org sized in the low thousands of seats leaves substantial headroom at the current funnel; an org approaching ~10K authenticating members/month would exceed the free cap (paid tier or contract discussion). Decision: no code gate; add an OPS-GOV go-live watch item (task 6.3) that documents the headroom math and the monitoring signal (Stytch project metrics) for when enterprise seat growth approaches the cap.
- **Per-project 5-connection budget vs. multi-org enterprise pipeline:** 5 SSO+SCIM connections are free *per project*; each additional connection bills at $125/conn/mo. Every enterprise customer org that adopts SSO or SCIM consumes one of the 5 free connections. **Commercial posture decision: pass-through** — connection usage beyond 5 is an Enterprise-tier feature; the marginal $125/conn/mo is absorbed into the Enterprise tier's ACV (enterprise ACV ≫ $125/mo), not itemized per customer. Documented in `STYTCH_CONFIGURATION.md` and pricing notes; no soft cap and no code gate (Stytch bills per connection; the overage is priced into the plan). If enterprise adoption outpaces the budget, the posture is revisited at pricing review (task 6.3).
- **Discovery-send email volume:** pre-built discovery sends fire on every login submission (including unknown addresses), replacing the pre-validated custom flow's lower volume. Assumed within the free email allowance at projected login volumes; verified at E2E (task 7.3) and re-assessed at task 6.3. Per-email abuse is bounded by Stytch's per-email rate limit (see `## Market Risk`).
- **Branding posture:** Stytch-branded emails are accepted (custom branding is $99/mo — skipped, per Non-Goals). For B2B procurement, SSO/SCIM feature parity outweighs branded-email aesthetics; consistent with the existing "no paid add-ons" stance.

## Market Risk

- **Email-bombing / spam-reputation surface (Colombia context):** the pre-built login sends discovery emails to any submitted address (custom pre-validation gone) — in a market with heavy WhatsApp/SMS abuse, sender-reputation risk is real. Mitigations: Stytch per-email rate limiting (sole send backstop), JIT off by default (no org revealed to unknown addresses), documented posture in `STYTCH_CONFIGURATION.md`, sender reputation monitored at E2E (task 7.3) and task 6.3.
- **Colombian-Spanish locale mismatch:** `StytchB2B` and the Admin Portal default to English; D8 pins `locale: "es"` + strings overrides (tasks 4.1/3.2). Failure mode: auth/SSO/SCIM surfaces break the product's Spanish mandate and hurt SMB/enterprise trust; verification is part of the FE tasks and `qa/` (Playwright).
- **Connection budget vs. Colombian SMB/enterprise mix:** SMB orgs stay within the free tier (few/no connections); enterprise adopters consume the 5-connection budget — the pass-through decision (above) keeps margin neutral at Enterprise ACV. Risk of budget exhaustion before the posture is revisited is low at the current pipeline and is re-assessed at task 6.3.
- **Stytch-branded emails posture:** accepted; procurement-trust risk is mitigated by SSO/SCIM feature parity (the enterprise gate) and is conditional on the market sections being present and coherent (council `MARKET: CONDITIONAL` — this section plus `## Market & Unit Economics` clear it).
- **Admin Portal availability risk:** if the portal is unavailable in reviewed SDK versions and the fallback (D4 Branch B) is chosen, SSO/SCIM management moves to custom Go-backed CRUD — a scope/sizing impact on FE tasks; the decision gate at task 3.2 de-risks this before FE sizing.

## Migration Plan

1. **Test project config (OPS-GOV):** enable SSO/SCIM/OAuth/email-OTP products; verify billing; register Google/Microsoft providers; leave JIT off.
2. **Backend first:** `OrgAuthPolicyUpdater` + adapter + routes + tests (no behavior change until UI flips).
3. **Frontend:** Admin Portal availability gate at task 3.2 (bump or fallback) → mount SSO/SCIM views (`?view=sso`/`?view=scim`) → flip `/auth` to `<StytchB2B>` (Spanish locale) → JIT toggle in `?view=access` (incl. SSO-JIT toggle).
4. **Prod rollout:** config mirrors test; existing orgs keep `NOT_ALLOWED` JIT + `auth_methods: ALL_ALLOWED` (first-write preserves the current method set); orgs opt in per admin action.
5. **Rollback:** Git revert; per-org Stytch state restored via `PUT /v1/b2b/organizations` (JIT → `NOT_ALLOWED`, `auth_methods` → `ALL_ALLOWED`/prior set, `sso_jit_provisioning` → `NOT_ALLOWED`); SSO/SCIM connections deleted via Admin Portal (or fallback CRUD) / `DELETE /v1/b2b/sso/{connection_id}`.
