# AGENTS.md

Guidance for AI coding agents (including MonkeyCode) working in this repository. Read this file before starting any task, and follow it for every change you make.

## Source of Truth: OpenSpec

This repository is **spec-driven**. The behavioural source of truth for the software does not live in the code — it lives in the OpenSpec tree:

- `openspec/specs/<capability>/spec.md` — **Living specifications**. Each capability (auth, CRM, billing, WhatsApp, etc.) has an authoritative spec of required behaviour. These are the source of truth for what the system must do.
- `openspec/changes/<change>/` — **Active change proposals**. Each contains `proposal.md`, `design.md`, `tasks.md`, and delta specs under `specs/` describing work that is planned or in progress. When a change is completed and archived, its deltas are folded into the living specs.
- `openspec/changes/archive/` — **Archived changes** whose deltas have already been merged into the living specs.
- `openspec/config.yaml` — OpenSpec configuration: schema, project context, and governance rules that all proposals, specs, designs, and tasks must obey.

## Mandatory Workflow for Every Code Task

1. **Read the relevant specs first.** Before writing or modifying any code, read every `openspec/specs/<capability>/spec.md` that applies to the code you will touch. If the spec describes a feature, endpoint, schema, permission, or status code, the implementation MUST match it.
2. **Check for active changes.** List `openspec/changes/` and read any active change that touches the same capability (its `proposal.md`, `design.md`, `tasks.md`, and delta specs). If your work matches an active change, implement against that change's artifacts and keep them up to date.
3. **Treat OpenSpec Markdown as authoritative.** Do not invent behaviour that contradicts the specs. Where code and spec disagree, the spec wins — adjust the code (or, if the spec is genuinely wrong, propose an OpenSpec change first).
4. **Never edit the OpenSpec tree casually.** `openspec/specs/` and `openspec/changes/` are versioned governance artifacts. Do not delete, move, or rewrite them. Behavioural changes go through a change proposal under `openspec/changes/<change>/`; they are not made by editing code in isolation.
5. **Three lifecycle gates (mandatory).** The workflow enforces three gates on every change:
   - **Premise validation (propose time):** factual claims in a proposal (existing components, routes, endpoints, build status) MUST be verified against the codebase before writing delta specs. Unverifiable claims go in the proposal's `## Assumptions` section — never assert them as facts.
   - **Verification gate (apply time):** before a change is reported complete, every verification command recorded in `tasks.md` MUST be run and pass. Failures keep the change in-progress and are recorded in `tasks.md`.
   - **Archive decision (after completion):** a completed change MUST NOT sit in silent limbo — either run `/opsx-archive` or record an explicit `**Archive deferred:** <reason>` entry in `tasks.md`.
   - Archive additionally BLOCKS when incomplete tasks are verification tasks; non-verification gaps only require confirmation.
6. **`openspec update` regeneration risk.** `.opencode/skills/openspec-*/SKILL.md` files are generated by the openspec CLI (`openspec update` can regenerate and overwrite them). The authoritative contract for these gates lives here in AGENTS.md and in `openspec/config.yaml`; if skills are regenerated, re-apply the gate steps to the new files.

## Project Context

Monorepo with two applications:

- `go-b2b-starter/` — Go 1.25 backend: Gin, PostgreSQL + SQLC (pgvector), Stytch B2B (auth/RBAC), Polar.sh (billing), AI/RAG. Clean Architecture enforced: `domain` -> `app` -> `infrastructure`, dependency injection via uber-go/dig. Key commands: `make dev`, `make server`, `make sqlc`, `make test`.
- `next_b2b_starter/` — Next.js 16 + React 19 frontend: TypeScript (strict), Tailwind, shadcn/ui, TanStack Query, Server Actions. Key commands: `pnpm dev`, `pnpm build`, `pnpm lint`.

### Dual Single Point of Truth (SSOT) Architecture

Extracted from `openspec/config.yaml` — follow these invariants:

- **Static SSOT** — this Git repository: authoritative for code, DB migrations, SQLC query models, OpenAPI schemas, and OpenSpec deltas. Code changes cannot alter these contracts without an archived OpenSpec change proposal.
- **Runtime SSOT** — Stytch B2B: sole authority for member identity, organization multi-tenancy, session validity, and RBAC. Local PostgreSQL MUST NOT store passwords, MFA tokens, or session tokens — store only `stytch_member_id` / `stytch_organization_id` foreign keys.
- Inbound requests are verified via Stytch B2B JWKS (local cache TTL <= 300s); Stytch webhooks are verified via `stytch-signature`/HMAC headers before any DB mutation; outbound Stytch API calls are wrapped in a two-tier circuit breaker (threshold 5, timeout 10s, half-open probe 2). On Stytch degradation, fall back to cached JWKS validation with read-only scope.

### Governance Rules (from `openspec/config.yaml`)

- **Proposals**: Any proposal modifying auth flow or data persistence MUST explicitly reference Stytch B2B API contracts, MUST define rollback strategies for both Git state and Stytch tenant policy state, and MUST include a "Non-Goals" section rejecting local credential storage.
- **Specs**: Define state-transition invariants across the Go/Stytch boundary, specify fallback/circuit-breaker states for every outbound Stytch SDK invocation, and map Stytch RBAC roles to local authorization contexts with strict type definitions.
- **Design**: Go domain models MUST NOT import Stytch SDKs or external transport packages; infrastructure adapters (`infrastructure/auth/stytch`) MUST implement domain interface abstractions; DB operations triggered by Stytch webhooks MUST be idempotent (transaction-isolated state checks).
- **Tasks**: Cap execution at 2 hours per task unit; tag tasks with `[BE-DOMAIN]`, `[BE-INFRA]`, `[DB-SQLC]`, `[FE-NEXT]`, or `[OPS-GOV]` (workflow/tooling tasks); require verification criteria covering signature-validation tests and mock fallback execution.

## Agent Pipeline (native Pi, replaces omp/Pantheon)

The repository runs its agent stages as native Pi prompt templates, chained headlessly by `scripts/pipeline.sh` (`pi -p --prompt-template .pi/prompts/<stage>.md "<change>"`; slash commands are TUI-only). Stage order: `architect` → `council` → [`revise` ⇄ `council`, bounded] → `sdet` → `uiux` → `iso`.

- `/architect` — thin wrapper delegating to the `/opsx-propose` workflow (planning artifacts only).
- `/council` — adversarial multi-persona review (security / DBA / SRE / Product-GTM / Colombia IT-Market) of `design.md`; writes `VERDICT.md` with a machine-parseable first `STATUS: (APPROVED|REJECTED)` line plus a `MARKET: PASS|CONDITIONAL|FAIL|N/A` line; the market-read lens applies to market-in-scope changes (billing/pricing, AI cost/metering, WhatsApp/Meta channel, compliance, marketing/signup funnel) and market-in-scope designs SHALL carry `## Market & Unit Economics` and `## Market Risk` sections. A `STATUS: REJECTED` verdict MUST include a numbered "Required design changes" list (the revise stage consumes it). `scripts/pipeline.sh` halts (exit 2) on `REJECTED` after the revision cap, exit 3 on an absent/ambiguous marker. Advisory `routing.json` fields `requires_market_read: true` and `requires_council: true` force the council regardless of `complexity`.
- `/revise` — thin wrapper over the `opsx-update` workflow (verdict-driven, never edits code): reads `VERDICT.md`'s numbered required design changes, revises the change's planning artifacts (`proposal.md`/`design.md`/`tasks.md`/delta specs) via paths provided in a transient `.revise-context.json`, writes the machine-parseable `revision.md` coverage sidecar, and runs with `--tools read,write` (no shell).
- `/sdet` — thin wrapper delegating to the `/opsx-apply` workflow (implementation + verification gate; council verdict recorded in `tasks.md` when required).
- `/uiux` — Playwright visual + accessibility QA at 390x844 / 768x1024 / 1440x900 → `openspec/changes/<change>/qa/`.
- `/iso` — compliance traceability updating `docs/compliance/ISO_TRACEABILITY_MATRIX.md`.

Stage gating is advisory via an optional `routing.json` sidecar in the change directory (`requires_council`, `requires_playwright`, `requires_iso`, `requires_market_read`, `complexity`); `pipeline.sh` supports `--with-council`, `--with-uiux`, `--skip-iso`, `--skip-revise`, `--max-revisions <N>` (default 2, `PIPELINE_MAX_REVISIONS` env), `--reset-revisions`, and `--dry-run`. A `REJECTED` council verdict triggers a bounded loop of up to `MAX_COUNCIL_REVISIONS` revise→re-review passes (each pass: write `.revise-context.json` → `revise` → `openspec validate` → council re-review); the revision counter persists in `revision.json` (change dir) so the cap is enforced across re-runs, is cleared on an approved re-review and by `--reset-revisions`, and `revision.md` is the never-deleted audit trail. Project-local extensions are declared in `.pi/settings.json` (`@bopstack/pi-codegraph`, `pi-playwright`, `pi-web-search`). omp/Pantheon artifacts are removed; `.pi/side-agent-*.sh` / `.pi/side-agents/` are `pi-side-agents` worktree machinery (installed by `scripts/bootstrap-stack.sh`), independent of omp and of this pipeline.

**Security / trust model:** every headless stage runs with `pi -p --approve` because non-interactive `-p` mode never shows a trust prompt and otherwise ignores project resources (extensions + `.pi/prompts/`) when no trust decision is saved. `--approve` trusts and executes project-local packages — i.e., the pinned third-party extensions run with full system access. Before adding an extension to `.pi/settings.json`, review its source; the current three (`@bopstack/pi-codegraph`, `pi-playwright`, `pi-web-search`) are reviewed pinned versions. The council and revise stages additionally run with `--tools read,write` (no shell, no git) so they can never mutate the repo beyond `VERDICT.md`/`revision.md` + planning artifacts. `jq` is a runtime prerequisite of `scripts/pipeline.sh`. `scripts/bootstrap-stack.sh` is legacy omp-era bootstrap tooling: its package installs now use `pi install -l` and its omp-style prompt generation is disabled (native templates ship in-repo).
